**段階 7：計測と調整（最優先）。** 今の誤差を数字で押さえ、制御の修正の効果を測ります。完了の目安は、S2 の平均誤差が直す前の半分前後になることです。

- [ ] 遅延を測る。カメラの前でストップウォッチを映し、画面に出た時刻との差を見る
- [ ] ループ Hz を見る。約 15 Hz（`loop_ms` が約 66 ms）なら `CAP_BUFFER=2` と比べる（課題 26）
- [ ] 直す前の基準を測る。修正前のコード（2026-11-18）で、`SAVE_FRAMES=false` を付けて S1〜S3 を測る
- [ ] 修正後のコードで S1〜S3 を測る
- [ ] `KD=0`、`KD=0.3`、`KD=0.6` を比べる。モデルでは差は 1〜2 cm
- [ ] 遅延が 100 ms 以下なら `KP=0.4` を試す。165 ms を超えていたら `KP=0.2` を試す
- [ ] 測ったループ周波数と遅延をモデル計算に入れ、モデルを答え合わせする。このモデルは 13 でも使う

調整の順番は「遅延を測る → KD を比べる → KP を試す」です。この制御は位置に足していく形なので、Kp は実質的に積分、Kd は実質的に比例として効きます。Kp は遅延が長いほど行き過ぎます。S1 で指令が細かく揺れる（ハンチング）なら、死帯を少し上げます（`DEAD_ZONE=1.5`）。

Kd の単位は以前と違います。新しい Kd = 以前の Kd ÷ dt です。元のロードマップの案「Kd 0.2 → 0.02」は、30 Hz では新しい単位で 0.6 に当たります。

**段階 8：配線強化とカメラの再キャリブレーション。** 線が抜けたり接触が悪くなったりするのをなくし、カメラの角度換算を正しくします。

- ネジ端子シールド、5V / GND の分配を基板かレバー式コネクタに、ロック付きコネクタ（JST-XH）
- サーボ用に別の 5V 電源（2A 以上、GND は共通）
- 3D プリンタでカメラとセンサーのマウントを作り、土台にネジ止め
- 付け直したら、IR カメラを 1280×720 でキャリブレーションし直す（課題 5）

再キャリブレーションは段階 11 の前までに済ませます。閉ループの追従では換算のずれはゲインのずれになるだけですが、角速度を使う予測（11）では誤差になります。

**段階 9：起動センサーを安定した方式に変える。** 9a（F25）のあともしばらく使って「反応しない」が残る場合だけ進みます。その場合の原因は、センサー本体か取り付けです。センサーが変わるとマウントの形も変わるので、8 と同時に決めます。

| 候補 | 良い点 | 気になる点 |
| --- | --- | --- |
| ミリ波レーダー | 止まっている人も検知でき、誤検知が少ない | 部品の追加と配線の変更が必要 |
| カメラの差分検知 | センサーを足さない。今の IR カメラで動きを見る | 待機中もカメラと Jetson が動き続ける |
| PIR の改善 | 部品はそのまま | 配線・取り付け・再検知の処理を見直しても限界がある |

**段階 10：コードの整理。** 残りは 5 節の 3 件（720p の既定化、person 専用モデル、シリアル受信の修正）です。前処理の GPU 化と INT8 化は後回しにします。ループはカメラの 30 fps で頭打ちで、推論はもう十分速いためです。

**段階 11：予測と追跡。** 遅延による追従遅れ（課題 3）と、人の乗り換え（課題 7）をなくします。

- 土台は「絶対角方式」にする。フレームを撮ったときのサーボ角 + 誤差 = 人の絶対角。これを状態にして、カルマンフィルタで角度と角速度を推定し、測った遅延の分だけ先を狙う。一瞬見失っても、予測でつなぐ
- 撮影時の指令角と人の絶対角は、もう CSV に記録している（`servo_at_capture_*`、`target_abs_*`、F27）。段階 7 の計測の CSV で、この方式を先に検討できる
- サーボは位置を読めないので、履歴にあるのは指令角。実際の角度との差は `SERVO_LAG_MS` で補う
- ID 追跡（ByteTrack など）で、同じ人を追い続ける
- 参考：rm_auto_aim（MIT）。「検出 → 追跡 → マイコンへ送信」という構成が PX と同じ
- ここでできた「PD 制御＋予測」を、13 の強化学習と比べるときの基準にする

**段階 12：サーボ制御をマイコンに移す（任意）。** 角度を 1° 刻みではなく 0.1° 刻みで、なめらかに動かします（課題 2 の残り）。

- 今は Arduino が「受け取った整数の角度をそのまま出すだけ」になっている
- 自作ファーム（RP2040 / STM32 / ESP32）に替える。Jetson は目標角と角速度を送り、マイコンが 200 Hz〜1 kHz で補間して動かす
- これで死帯を 0.5° まで下げられる
- 任意：位置を読めるシリアルサーボか、ジンバル用モーターに替える。段階 11 の「指令角と実際の角度の差」もなくなる

**段階 13：強化学習（シミュレーション → 実機）。** 制御を強化学習で学ばせ、シミュレーションで学んだものを実機で動かします（sim-to-real）。

- 保管してある MuJoCo のシミュレーションを戻し、学習環境（Gymnasium）にする
- 遅延・ノイズ・サーボの特性・歩き方をランダムに変えて、PPO で学習させる。ランダムにする範囲は 7 の実測値から決める
- DGX で学習 → ONNX → TensorRT で Jetson に載せ、実機で低速から確かめる
- 11 の「PD 制御＋予測」と、同じシナリオ（S1〜S3）で比べる

### 6.2 評価方法

どの段階も、同じ 3 つのシナリオで前後を測り、記録表に数字を残します。床の、カメラから 5 m の位置に、横 4 m の線を貼っておきます。

| シナリオ | やり方 | 見る数字 |
| --- | --- | --- |
| S1 静止 | 5 m 先に 30 秒立つ | 誤差の平均、1 秒あたりの指令の変化回数（ハンチングの有無） |
| S2 普通の歩行 | 線の上を約 1.3 m/s（4 m を約 3 秒）で 5 往復 | 誤差の平均と 95% 値（度と cm）、見失った回数 |
| S3 ゆっくり歩行 | 同じ線を約 0.7 m/s で 5 往復 | S2 と同じ |

数字は次の手順で取れます。

```bash
# コンテナ内。シナリオごとに CSV を分ける
TIMING_CSV=/ros2_ws/work/bench/results/stage7/live_s2.csv PROVIDER=trt ./launch_px.sh
python3 bench/summarize.py bench/results/stage7 --distance-m 5
```

集計の「追従」の表に、検出率、ループ Hz、横の誤差の平均と 95% 値（度と cm）、指令変化 / 秒（横と縦）、取りこぼしの回数、WATCH に戻った回数、フレームの古さが出ます。誤差は、検出できたフレームでの「画像の中心からのずれ」です。見失っている間のずれは入らないので、必ず検出率と一緒に見ます。

修正前のコードの CSV には誤差の列が無いので、基準（段階 6 完了時）で数字として取れるのはループ Hz と推論時間です。誤差は目視か、動画から測ります。

### 6.4 モデル計算による見積もり（実測ではありません）

人が 5 m 先を横に 1.3 m/s で歩く場合の平均誤差です。元のロードマップの数字をそのまま載せています。`px_track_sim.py` を受け取っていないため、この数字は検証できていません。

| ケース | 平均誤差 |
| --- | --- |
| 以前（CPU、12 Hz、制御そのまま） | 約 79 cm |
| 今（TensorRT、30 Hz、制御そのまま） | 約 53 cm |
| ＋ 制御の修正（段階 7、12） | 約 11 cm |
| ＋ 速度の予測（段階 11） | 約 3 cm |

「今」の 53 cm は 30 Hz を前提にしています。修正前のコードを普段どおり起動すると PNG を 2 枚保存していたので（課題 12）、実際のループは 30 Hz より遅かった可能性があります。実測がこの見積もりと大きくずれたら、測った周波数と遅延でモデルの方を直してから次に進みます。

遅延と Kp の目安です。別の簡易モデルでの見積もりで、Kd はどれも 0.3 です。

| 遅延 | Kp 0.2 | Kp 0.3（既定） | Kp 0.4 |
| --- | --- | --- | --- |
| 約 100 ms | 安定 | 安定 | 安定 |
| 約 130 ms | 安定 | 安定 | 揺れ始める |
| 約 165 ms | 安定 | 揺れ始める | 発振 |
| 約 200 ms | 安定 | 発振 | 発振 |

修正のレビューのモデル計算では、絶対角方式（予測なし）は遅延 150 ms でも揺れません（S1 の指令変化 0.4 回 / 秒）。ただし動く人には遅れます（S2 平均誤差 28 cm）。予測と組み合わせる前提です。

### 6.5 訂正と補足

**課題 13 の訂正。** 当初は「最大約 300 ms 古い角度を書く」と見立てましたが、測ると違いました。33 ms 均等で送ると、元のコードでも遅れは平均 0.4 ms でした。15・15・69 ms の繰り返し（平均は同じ 30 Hz）で送ると、元のコードは平均 12.9 ms、最大 28.4 ms、修正後は平均 1.3 ms、最大 5.0 ms です（PC 上、仮想シリアルでの計測）。30 fps のカメラでは、指令が溜まり続けることはありません。

**課題 5 の記述の訂正。** 元のロードマップは「別のカメラ（BRIO、720p）の値を流用」としていましたが、コードはすでに IR カメラ用のファイル（2026-07-19 撮影、63 枚）を読んでいます。問題は、そのファイルの値が不自然なことです。

**課題 14 の中身。** 取りこぼす経路は 3 つありました。

1. WATCH に戻った直後、PIR が HIGH のままだと新しい立ち上がりが来ない。コードはピン設定の再送で今の値が報告されることを期待していたが、Telemetrix が実際にそう動くかは未確認
2. 報告が来ても、watch_node のリセットより先に届くと捨てられる
3. px2 は、px3 の準備前に来た起動要求を消してしまう

F25 でこの 3 つを直しました。PC 上で「HIGH を 1 回だけ報告し、再送には答えない Arduino」を作って比べると、修正前は最初に WATCH に戻ったあと 75 秒間 1 度も起動せず、修正後は約 1.1 秒後に再起動しました。修正後は、WATCH に戻ってから 1 秒は再起動しません（`REWAKE_DELAY_MS`）。人がいないのに PIR が HIGH のままの間は、約 2 秒おきに DETECT と WATCH を往復します。

**リポジトリのファイル。** `.clang-format` と `.gitignore`（F18）は、推定・新規に作ったものです。以前作ったファイルが手元にあれば、それで置き換えます。

### 6.6 対象外・保留

- RMVision（参考にした公開コード）は、コードを使いません。ライセンスの表記がなく、古いためです。「重い検出と軽い追跡を組み合わせる」考え方だけを 11 で使います

- 「検出を数フレームに 1 回にして、その間を追跡で埋める」は必須でなくなりました。TensorRT で毎フレーム検出できるからです
- 校正と取り込みの解像度を CI で調べる案は見送りました。解像度は起動時の変数で変わるので、起動時の警告にしました

### 6.7 用語

| 用語 | 意味 |
| --- | --- |
| PD 制御 | 誤差に比例する量（P）と、誤差の変化に比例する量（D）を足して、動かす量を決める制御 |
| 増分 PD 制御 | PD 制御で決めた量を、今の位置に足していく形。PX はこの形。位置で見ると、Kp は実質的に積分、Kd は実質的に比例として効く |
| 死帯 | 誤差がこの値より小さければ動かさない範囲。小さな揺れでサーボが震えるのを防ぐ |
| ハンチング | 目標の周りを行ったり来たりして、指令が細かく揺れること |
| 絶対角方式 | フレームを撮ったときのサーボ角に誤差を足して、人の絶対角を出し、そこへ向ける方式。段階 11 の土台 |
| TensorRT | NVIDIA の GPU 向け推論エンジン。FP16 / FP32 は計算の精度（ビット数） |
| カルマンフィルタ | 揺れる測定値から、位置と速度を推定する方法。少し先の位置を予測できる |
| sim-to-real | シミュレーションで学習した制御を、実機で動かすこと |
| モデル計算 | 制御ループを簡単に模した計算（`px_track_sim.py`）。実測ではなく、改良の効果を比べるための見積もり |
| F01〜F27 | 2026-11-19 にコードへ入れた修正の ID。修正記録（`docs/04_fix_log_2026-11-19.md`）に箇所と確認項目がある |
| R、C | 修正 F01〜F17 のレビュー結果（`docs/06_review_of_fixes_F01-F17.md`）の指摘の番号 |
